## 一、论文翻译（要点版）

### 摘要
系统事件日志是提升系统健康与稳定性的宝贵数据资源。典型的日志分析流程是：先**解析非结构化日志**，再对结构化数据做分析。以往的方法都是**离线批处理**原始日志文件，但越来越多应用要求**在线监控与处理**。本文提出在线流式方法 **Spell**，基于**最长公共子序列（LCS）** 解析系统事件日志，以流式方式动态提取日志模板并维护已发现的消息类型集合。在大规模真实日志上的评测表明，即使与离线方法相比，Spell 在**效率与效果**上都更优。

### 1. 引言
现代系统日益复杂，要求能即时告警并缓解问题，因此**流式在线异常检测**很有吸引力。系统日志蕴含使用模式、执行路径、运行状态等关键信息。

大部分先前工作的首要步骤是把非结构化日志解析成结构化数据——用正则、源码、或聚类/迭代划分等数据挖掘方法。但除需要专家知识的**正则方法**和常常拿不到源码的**源码方法**外，此前**没有任何方法能真正在线流式解析**；有些号称"online"，实则先做大量离线处理，再用得到的模板去匹配新日志。

日志管理系统（如 Splunk、Elastic Stack）默认解析器只能解析时间戳、主机名等简单 schema，日志正文被当作非结构化文本。一个能在线把事件日志解析成结构化数据的方案，能让日志更易查询、汇总、聚合。

一条日志由源码中的 `printf` 语句产生，可视为（"消息类型", "参数值"）对的集合。例如 `printf("File %d finished.", id)` 产生的消息类型是 `File * finished`，`*` 是参数占位符。结构化日志解析器的目标就是识别出这类消息类型。

**贡献**：提出 Spell（Streaming Parser for Event Logs using LCS），以在线流式方式把非结构化日志解析为消息类型和参数，处理每条日志的**时间复杂度接近线性**（相对于日志长度），且效果/效率均优于离线 SOTA。

### 2. 问题与背景

**问题定义**：给定按时间戳排序的日志条目集合 `log={e1,...,eL}`，由 `m` 个不同打印语句、`p` 个程序产生（`m, p` 及语句、源码均未知），结构化日志解析器要解析出全部 `m` 个消息类型。目标是设计**流式**解析器——只扫描一遍日志，逐条在线处理。

**相关工作**：
- 用源码 schema 提取类型 [Xu 等, SOSP'09]
- 预定义领域正则 [Beschastnikh 等, ICSE'14]
- 加权编辑距离聚类 + 递归切分 [Fu 等, ICDM'09]（即 CLP）
- IPLoM：按长度、少歧义位置、二分映射迭代划分 [Makanju 等, TKDE'12]
- LogTree、LogSig、HELO、HLAer 等
- 结论：所有已有方法都是**离线批处理**，或用离线模板/正则去匹配新日志

### 3. Spell：流式结构化日志解析器

Spell = Streaming structured Parser for Event Logs using **LCS**。

**A. LCS 问题**：两个序列的最长公共子序列。核心观察：同一个打印语句产生的两条日志，其常量部分（消息类型）往往占主体，参数值只占小部分；参数不同但语句相同的两条日志，其 LCS 极可能就是源码里的常量，即消息类型。

**B. 基本记号与数据结构**
- **token**：日志条目按分隔符（空格、等号等）切分出的词
- **LCSObject**：含一个 `LCSseq`（候选消息类型）和 `lineIds`（产生该序列的日志行号列表）
- **LCSMap**：当前所有 LCSObject 的列表

**C. 基本工作流**（图1）
新日志 `ei` 到达 → 切分为 token 序列 `si` → 与 LCSMap 中每个 `LCSseq(qi)` 计算 `ℓi = |LCS(qi, si)|`，记录最大 `ℓj`。
- 若 `ℓj ≥ τ`（默认 `τ = |s|/2`，即序列长度的一半）→ 认为 `qj` 与 `s` 是同一消息类型。
  - 若多个并列最大，选 `|qj|` 最小的（与 s 集合相似度最高）
  - 用**回溯**生成新 LCS 序列作为该类型；两序列不一致处标记为 `*`（参数占位符），相邻 `*` 合并为一个
  - 更新第 j 个 LCSObject 的 `LCSseq` 并加入行号 `i`
- 若所有 `qi` 与 `s` 的 LCS 都不足 `|s|/2` → 为 `e` 新建 LCSObject，其 `LCSseq = s`

**D. 效率优化（核心创新）**
基础方法每来一条日志都要和所有已有消息类型算 LCS，复杂度 `O(m·n²)`（n 为 token 数，m 为消息类型数）。由于绝大多数（评测中 >99.9%）新日志的消息类型**已存在于 LCSMap**，引入**预过滤（pre-filtering）**步骤：

1. **简单循环法**：遍历 strs，用双指针判断 `stri` 是否为 `σ` 的子序列，剪枝掉长度 `< |σ|/2` 的；最坏 `O(m·n)`。
2. **前缀树法**（图2）：把已有消息类型建前缀树 `T`。对 `σ` 逐字符与 `T` 比较，高效剪掉多数分支，未被任何节点匹配的字符即参数。大多数日志类型已在树中，时间复杂度仅 **`O(n)`**（最优，因至少需遍历一遍 token）。
   - 注意：前缀树只保证返回"是子序列的 stri"，**不保证返回最长的那个**（例：`σ=DAPBC`, strs={DA, ABC} 返回 DA 而非 ABC）。但实践中因参数多在末尾，前缀树结果与简单循环几乎一致（Los Alamos 43 万条日志 100% 一致）。
3. **完整预过滤流程**：先前缀树 → 未命中再用简单循环 → 仍失败时（<0.1%）才对所有消息类型：
   - 先用 **Jaccard 相似度** 过滤（与 e 公共 token 数 > 一半者）再做 LCS；
   - LCS 长度 `> |s|/2` 则调整该类型与树；否则把 e 作为新消息类型加入树和 LCSMap。

**E. 时间复杂度分析**
LCSMap 大小 ≤ 消息类型总数 `m`（常数）。基础 Spell 为 `O(m·n²)`；加预过滤后，设预过滤失败条数 `F`、简单循环命中 `I`，摊还成本 ≈ `O(n + (I+F)/L·m·n + F/L·m·n²)`。评测中 `(I+F)/L < 0.01`、`F/L < 0.001`，故每条实际仅 **`O(n)`**。

**F. 备注**：没有一种自动方法对所有日志完美（连基于源码的方法也非 100%）。

### 4. 评测
对比两个离线 SOTA：**IPLoM**（轻量，按长度/位置/二分映射迭代划分）和 **CLP**（加权编辑距离聚类 + 递归划分）。参数见表 I。数据集见表 II：
- **Los Alamos HPC log**：433,490 条
- **BlueGene/L log**：4,747,963 条

**A. 效率**（图3、表 III、表 IV）
- Los Alamos：naive LCS 约 75s，加预过滤仅 **9s**；IPLoM 最快；CLP 慢 2–4 个数量级（>10万条就跑不完）。
- BlueGene：CLP 直接跑不完；**Spell（预过滤）效率甚至超过 IPLoM**。
- 预过滤各步命中率：前缀树 91.68% / 93.89%，简单循环 8.23% / 6.07%，naive LCS 仅 0.09% / 0.042%。
- 单条查找耗时：前缀树 0.006/0.011ms，简单循环 0.020/0.087ms，naive LCS 0.175/0.580ms。

**B. 效果**（图4、表 V）
- Spell 准确率在两个数据集上均明显优于 IPLoM 和 CLP（IPLoM 在 BlueGene 上表现很差）。
- 预过滤对准确率几乎无影响：Los Alamos 准确率 0.822786（有无预过滤相同），BlueGene 0.811798 vs 0.811791。

### 5. 结论
Spell 是流式结构化日志解析器，适合在线日志挖掘与监控，也是现代日志管理系统的有力补充。预过滤大幅降低了开销，实测表明 Spell 在效率与效果上均优于离线 SOTA。

## 三、关键实现提炼（可用于工程落地）

### 核心数据结构
```text
LCSObject { LCSseq: List[token], lineIds: Set[int] }
LCSMap:   List[LCSObject]
PrefixTree: 索引所有已知消息类型（token 序列）
```

### 主流程（每条日志 e）
1. 用分隔符切分 `e` → token 序列 `s`；`n = len(s)`；`τ = n/2`
2. **前缀树查找**：逐 token 沿树走，未被匹配的 token 记为参数；若匹配的 `stri` 长度 `≥ τ` → 命中，更新对应 LCSObject 的 `LCSseq`，加入行号
3. 否则 **简单循环**：遍历 LCSMap 各 `qi`，双指针判断 `qi` 是否为 `s` 子序列，记录满足条件且 `|LCS|≥τ` 者（并列取 `|qi|` 最小）
4. 仍无命中 → 遍历所有 `qi`，先算 **Jaccard**，`Jaccard>0.5` 者再算 LCS；若 `|LCS(qi,s)|>τ` 则回溯生成新 `LCSseq`（不一致处标 `*`，相邻 `*` 合并），更新对象与树；否则 `e` 作为**新消息类型**新建 LCSObject 并插入树
5. **回溯生成 LCS 序列**：标准 LCS DP + 回溯，在分歧位置插入 `*`

### 关键参数
- 消息类型阈值 `τ = 0.5`（即 `|s|/2`）
- 预过滤失败率 < 0.1%，naive LCS 仅用于 < 0.1% 日志

### 性能要点
- 99%+ 的日志在前缀树 / `O(n)` 内完成
- LCSMap 大小有界（≤ 实际消息类型数 m，常数级）
- 单条查找摊还 `O(n)`，实测毫秒级

### 与离线法对比结论
Spell 准确率更高（尤其大规模异构日志），且能在线流式处理，无需离线预训练或源码/正则。
